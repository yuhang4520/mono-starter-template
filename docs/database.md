# 数据模型与迁移

`packages/db` 管理唯一 schema 和迁移历史。数据库连接优先使用进程环境变量，CLI 的本地回退文件是 `packages/db/.env`。应用分别加载自身环境文件，不再让 DB CLI 隐式读取 Admin 配置。

## 本次增量

- `0000` 保留原认证表迁移。
- `0001` 新增 `notes`：UUID 主键、组织外键、创建者外键、title/body、createdAt/updatedAt；索引 `(organization_id, created_at)` 用于组织内列表。组织删除级联删除笔记；用户删除后创建者置空，保留组织内容。
- `0002` 对 `members(organization_id, user_id)` 增加唯一索引，避免同一账号在同一组织重复产生成员关系。服务端仍检查实时成员角色和组织锁定状态，唯一约束不能替代授权。

组织创建和 owner 成员创建在同一事务内；成员添加的并发由事务锁与唯一索引共同约束。成员与笔记写入均将授权检查和业务写入放在同一事务，按组织→操作者用户→操作者成员顺序加锁，避免检查之后降权、移除、封禁或锁组织仍继续写入。成员变更使用组织排他行锁串行化，笔记写入使用共享行锁；所有更新/删除仍同时限定记录 ID 与 organizationId。平台封禁与会话撤销在同一事务执行；首次管理员初始化使用事务级锁防止并发初始化。

这些授权锁不新增表、索引或迁移；代价是同一组织的成员变更会排队，事务应保持短小，不在锁内调用外部服务。权限变更等待已经持锁的写事务提交，后续写入再检查新权限；不回溯撤销已经提交的数据。

新模板使用空库→migrate。`docker compose` 不再挂载一份复制的初始 SQL，避免它与 Drizzle journal 不一致。重复执行 migrate 不会重复建表。

## 旧库升级前检查

如果旧库已经用 `drizzle-kit migrate` 建表，保留 journal，按顺序执行新增迁移。先检查重复成员：

```sql
SELECT organization_id, user_id, COUNT(*)
FROM members
GROUP BY organization_id, user_id
HAVING COUNT(*) > 1;
```

发现重复时先备份并核对角色、邀请、关联记录，再由维护者决定保留哪条；模板不会自动删除历史成员。未经处理，唯一索引迁移会失败并阻止应用发布。

如果旧库通过 `docker-init/01-init.sql` 或 `db push` 建表而没有 `drizzle.__drizzle_migrations`，不能直接运行首次建表 SQL，也不能伪造 journal 假定 schema 相同。开发库无保留数据时使用独立新卷/新数据库；需保留数据时先备份、对比实际 schema 与 `0000`，制定专门的 baseline 迁移并在恢复副本验证。不要为本次模板升级删除已有业务卷。

## 发布与回滚

先运行本次提交的 migration 镜像，确认 Job 成功，再更新应用配置和镜像。迁移失败不发布应用。兼容性优先使用新增表/可空字段、回填、再约束的分阶段方式。

本次迁移不删除既有表/字段；旧应用可以继续运行，但 members 的新唯一约束会拒绝以前允许的重复写入。回滚镜像不会撤销 schema；不要用删除 notes 表回滚，它会损失新增数据。约束回退也应作为单独审查的 migration，而不是修改历史 SQL。
